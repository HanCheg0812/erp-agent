# Web 前端性能与 DOM 审计

日期：2026-09-29。状态：已测量，尚未修改产品代码。

## 范围与方法

- 在 Chrome/Playwright 中加载当前 Web 的完整 `App` 和未改动的生产构建；只拦截 `/v1`，注入合成的 50 个侧栏任务、50/200 条历史消息和每 35ms 一条的 reasoning/answer SSE 增量。另用开发构建注入计数器记录 React 组件调用和 Profiler commit；开发构建的 StrictMode 会使函数调用次数翻倍。没有调用真实模型或 ERP。
- 用 `MutationObserver` 分区记录新增/移除元素和属性变化，保留旧消息、当前段落及跳转按钮的节点引用；用 RAF、Long Tasks、Chrome Performance 域、强制 GC 和连续切换任务观察帧间隔、布局耗时与节点数。桌面为 1440x1000；390x844 手机视口和长历史/长段落压力场景使用 Chrome 4x CPU 限速。4x 限速不是实体手机基准。
- 原始报告、临时脚本、截图和录屏见 `/tmp/forge-web-dom-audit-20260929/`；单独的开发构建组件计数报告见 `/tmp/forge-web-dom-audit-dev-probe-20260929/report.json`。登录、记忆和运行管理入口的补测见 `/tmp/forge-web-dom-audit-20260929/surfaces.json`。有效运行均无页面异常或意外 API 请求；主聊天区截图没有横向溢出。这些本机合成数据不代表生产性能验收。

## 观察

| 场景 | DOM 与帧表现 |
| --- | --- |
| 50 条历史、桌面、正常 CPU | 初始 3,426 个元素。80 条 reasoning 和 80 条正文增量各新增 880 个词 span、移除 0 个；两段 RAF 间隔 P95 都为 16.7ms，长任务均为 0。旧消息、当前段落和跳转按钮一直是同一节点。 |
| 50 条历史、390px、4x CPU | reasoning/正文 P95 分别为 50/50.1ms，长任务分别 11/17 个；布局累计 548/477ms。帧已明显不连续，尽管没有旧正文的 DOM 重建。 |
| 加载至 200 条历史、1440px、4x CPU | 元素数从 3,427 涨至 12,726；加载较早消息时 P95 为 133ms。后续 80 条 reasoning/正文增量的 P95 约 100/100ms，长任务 23/33 个，正文结束时达 14,659 个元素。 |
| 已有 20,000 字单段回复、390px、4x CPU | 初始 14,851 个元素，其中 11,438 个淡入词 span。再追加 80 条正文增量时 RAF 间隔 P95 约 1,200ms，最长 Long Task 1,112ms，Chrome 累计布局约 5.9s；该段耗时约 55s。这里刻意构造超长单段且快速推送，是退化上界，不是常见回复的测量值。 |

- 普通流式增量只给当前 reasoning/正文追加词节点，并在 650ms 动画结束时改动已有 span 的 `class`；旧历史消息和当前段落均未被替换。完成快照仅更新当前正文的 `data-streaming`/`aria-busy`，思考过程收起/展开只切换 `aria-expanded`、`data-expanded`、`inert`、`tabIndex`，没有删除思考正文节点。切换任务则按当前 `CaseChat` 的 key 正常卸载/重建另一会话。
- 用户上滑后继续推送 10 条增量，四个生产构建场景的阅读位置漂移均为 0；点击“回到最新消息”后 `scrollTop` 等于当前最大值。始终只有一个 `.chat-scroll`。12 次任务切换后，同一会话采样点的节点数和监听器数稳定；本轮没有证据认定持续内存泄漏，短时堆大小变化不能作此结论。
- 开发构建中，输入 40 个字符产生 42 次 commit：`Workspace` 调用 84 次，50 个 `CaseRow` 合计调用 4,200 次；历史消息 DOM 不变。焦点触发内容未变的快照刷新时，50 个 `SavedMessage` 合计调用 100 次，旧节点仍保留。80 条 SSE 增量中历史消息没有跟着重渲染，只有最新消息进入更新路径。组件调用数包含 StrictMode 双调用。
- 其他入口在 4x CPU 合成夹具下补测：登录表单输入并切换注册/密码可见状态，DOM 增删各 9 个元素、RAF P95 16.7ms、无长任务；50 条个人记忆打开并输入时增加 479 个元素、P95 16.7ms、无长任务，原聊天和首条历史消息仍是同一节点，输入期间首条记忆节点也不变。关闭记忆移除 478 个元素，这是弹窗正常卸载。
- 运行管理使用 50 个候选、50 个模板、50 个实例、20 个节点和 50 条发布记录。打开入口时移除聊天主视图 1,155 个元素并挂载 817 个管理页元素，RAF P95 49.9ms、一个 50ms 长任务；切换实例/节点/发布/模板标签时，表格按预期卸载和挂载，P95 为 16.7-16.8ms、无长任务。返回聊天重新挂载 1,156 个元素，P95 50ms、两个最长 62ms 的长任务。这里是路由视图切换成本，不是聊天流式更新时的 DOM 闪动。

## 归因与后续

1. 长单段是最高风险。`AgentReply.tsx` 的淡入插件按词创建 span 并在每次流式解析时处理整块文本；完成后 `streamed.current` 仍保持流式 DOM，以避免用户已指出的收尾闪动。词 span 不会因动画结束自动合并，所以长块的节点数和解析/布局成本持续增加。后续应测量并限制长块增量工作的规模，同时保留新词淡入、旧节点稳定和完成时无重排的行为；不能直接切换完成态渲染模式来换取指标。
2. 历史消息在 `useConversation.loadEarlier` 中持续合并并全部挂载到 `CaseChat` 的单一消息列表。200 条历史的退化已测到；后续可在同一 `.chat-scroll` 内限制实际挂载窗口，同时保持加载更早消息、阅读锚点、跳转最新、方案和证据入口。不拆成两个滚动区。
3. 草稿写入位于 `App.Workspace` 的 `chatSessions`，每个按键触发整个侧栏的非 memo `CaseRow` 重渲染；当前主要是 React 计算浪费，尚未观察到侧栏 DOM 被替换。可隔离草稿状态或稳定侧栏行回调，再用组件计数和真实输入延迟复测。
4. `useConversation.merge` 在相同快照刷新时也用服务端新对象覆盖同 ID 消息，破坏 `SavedMessage` 的浅比较。应仅在消息内容/版本实际变化时替换对象，并覆盖恢复、权限和运行状态变化的回归。每条 SSE 当前也立即提交一次 React 更新；是否按帧合批需在真实 SSE 节奏和断线恢复语义下单独验证。

下一轮需要在真实用户设备或同等硬件上录制长回复与 200+ 历史的 Performance trace，先确认解析、React commit、布局各自占比，再逐项修复和复测滚动/淡入/思考框稳定性。本次仅为前端审计，不改变已验收的交互行为。
