# Agent runtime concurrency probe

Date: 2026-09-23. Scope: Rust API, separate worker processes, PostgreSQL, and a controlled runtime fixture. This is not a JCode, DeepSeek, or Cube-resident load benchmark.

The previous worker awaited each case turn in a loop. The worker now admits up to `AGENT_MAX_CONCURRENT_RUNS` independent cases at once (default 4, valid 1-8). A local in-flight case set and PostgreSQL advisory lock keep one active turn per case, including across API processes. Messages and approval decisions wake the worker immediately after transaction commit; task completion also triggers the next scan. A five-second periodic scan covers process startup, recovery, and notifications missed across processes. PostgreSQL remains the durable queue and source of truth. Queued runs are considered before waiting runs. Shutdown drains active tasks; existing session checkpoint and recovery rules still apply.

Each input has its own durable `agent_runs` row, keyed by message. One case has at most one active run so turns preserve conversation order; independent cases can run concurrently. A single PostgreSQL table does not imply one consumer: the HTTP process may set `AGENT_WORKER_ENABLED=0`, while any number of `erp-agent-api worker` processes claim work. `LISTEN erp_agent_runs` wakes each process after the enqueue transaction commits; a database trigger emits the notification, and a five-second scan remains the recovery fallback. Each worker needs its own PostgreSQL connection for notifications. The queue row and advisory lock, not the notification payload, decide ownership. Splitting one dependent model/tool loop into separate queue rows would add handoff latency and complicate recovery; independent tool calls inside the loop can still run concurrently where the harness allows it. Ingestion should use its own work class and concurrency limit so a large parsing backlog cannot monopolize interactive turns.

The notification migration must appear in `src/platform/service.rs`'s explicit `MIGRATIONS` list. An initial benchmark ran without that registration and was actually using the five-second poll. This was fixed and a registry test now checks every SQL migration file; the measurements below use the applied migration and count 50 PostgreSQL notifications for 50 submitted runs.

`tests/system/test-rust-api.mjs` starts one API process with the limit set to 4, then submits separate cases in batches of 1, 2, 4, and 8. Each runtime fixture holds for 2 seconds and emits a first text token afterward. The test checks every run completes, bounds simultaneous runs at 4, and retains the existing second-process same-case lock, cancellation, restart, approval, and compaction checks. Queue is message creation to `started_at`; TTFT is message creation to first persisted nonempty text event; total is message creation to terminal state. Timestamps come from PostgreSQL. Nearest-rank P50/P95 below describe this single, small synthetic run; they are not a stable service SLO.

The test prints its own `PERF` JSON lines on every execution so later changes can be compared against fresh measurements. `npm run check` includes this system test.

## 50-user process comparison

`node --env-file=.env scripts/bench-agent-workers.mjs --users=50 --workers=N --concurrency=8` creates a temporary database and 50 distinct users/cases, starts one API process with its worker disabled plus N separate workers, and sends one message per user concurrently. The synthetic runtime waits two seconds and then emits a first token. Every measured run completed, and the temporary database/processes were removed. These single-round nearest-rank percentiles show the dispatch and scheduling behavior, not provider or Cube capacity.

| Workers x slots | Peak active | Queue P95 | First token P95 | Completed P95 | Batch wall |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 x 8 | 8 | 10,435 ms | 12,487 ms | 12,490 ms | 14,674 ms |
| 2 x 8 | 16 | 4,335 ms | 6,394 ms | 6,398 ms | 8,590 ms |
| 4 x 8 | 32 | 2,272 ms | 4,315 ms | 4,319 ms | 4,524 ms |
| 8 x 8 | 50 | 445 ms | 2,531 ms | 2,536 ms | 2,723 ms |

The 8 x 8 warm second round completed 50/50 with 50 active, queue P95 99 ms, completion P95 2,239 ms and 2,401 ms wall time. The 8 x 4 comparison also had 32 slots and a 4,296 ms cold completion P95, close to 4 x 8; available slots, rather than the number of PostgreSQL queues, dominated this controlled workload. Real turns add model rate limits, token length, Cube placement, MCP/ERP latency, database connections and memory. Do not set production slots from this fixture alone.

The local preview now runs one HTTP API process without an integrated worker and eight independent worker processes with eight slots each (64 slots total). After switching from four workers, the API returned `/ready`, eight PostgreSQL listener sessions were present, and a fresh real DeepSeek Flash conversation completed with the requested short reply through a standalone worker. The earlier 4 x 4, 50-user synthetic probe remains a comparison: both rounds completed 50/50, reached 16 active turns, and measured completion P95 6,345 ms cold / 6,278 ms warm, with 8,396 / 8,414 ms batch wall. The 8 x 8 synthetic results above used the same worker topology in an isolated database. Neither probe is a real-model 50-user load test. The local services are transient user systemd units and will need restarting after a machine reboot.

## 50-user real-model probe and database limit

On 2026-09-23, `node --env-file=.env scripts/bench-agent-workers.mjs --live --users=50 --workers=8 --concurrency=8` used 50 separate synthetic accounts/conversations in a temporary database on the local PostgreSQL instance. Each request asked DeepSeek Flash with `low` reasoning for a short arithmetic answer; no ERP, Cube or knowledge tool was called. The script checked the reply for `323`. The first run completed 50/50 but peaked at 47 active, with queue P95 4,349 ms, first body token P95 5,546 ms, completion P95 5,595 ms and 49/50 observed reasoning steps. A subsequent controlled-runtime run also peaked at 47; PostgreSQL logged `FATAL: sorry, too many clients already`. Its `max_connections` was 100. The API uses a `deadpool-postgres` pool capped at 16 **per process**, and each active worker turn holds a PostgreSQL session-level advisory lock on a connection. The HTTP process, eight worker processes, benchmark clients and JCode storage calls share the instance limit. Per-process pooling therefore did not prevent exhaustion.

The worker now retries a queue scan every 100 ms while it has free slots and can still see queued tasks, including after another process wins a claim. A separate ephemeral PostgreSQL container with `max_connections=200` then reached 50 active and completed 50/50: queue P95 303 ms, first body token P95 5,087 ms, completion P95 5,139 ms. It observed reasoning in 48/50 and the expected answer in 49/50. This is one short-prompt run, not an accuracy or capacity guarantee.

The local development PostgreSQL Compose service now starts with `max_connections=${POSTGRES_MAX_CONNECTIONS:-200}`. It was recreated with the existing named data volume after checking that no Agent run was queued, running or waiting. Its `/ready` check returned 200. A second 50-user controlled-runtime run on this instance reached 50 active, completed 50/50, and saw queue P95 354 ms and 90 peak connections in the temporary test database. The final real-model run reached 50 active and completed 50/50 with the expected answer in 50/50; queue P95 was 329 ms, first *persisted* nonempty reasoning P95 was 4,750 ms among 49 observed reasoning replies, first body token P95 4,815 ms, completion P95 4,880 ms and whole-batch wall time 5,238 ms. The reasoning-visible time is measured by 100 ms database polling and can lag the underlying event; the other timestamps come from PostgreSQL. These are single-run nearest-rank percentiles, not a service SLO or proof for long tool-using turns.

Connection budgeting remains necessary before deployment. Raising PostgreSQL's limit is a local test configuration, not a substitute for a configured shared pooler or reducing per-turn connection tenure. Monitor total connections, pool waits, failed connection attempts, provider limits and memory with representative conversations before changing worker slots. The benchmark creates/drops its own database and test processes; it does not alter existing conversations.

To run separate workers locally, build the API, apply migrations, set `AGENT_WORKER_ENABLED=0` on the HTTP process, then start multiple `npm run dev:worker` processes with `AGENT_MAX_CONCURRENT_RUNS` set for each. Each worker needs `AGENT_STORAGE_ORIGIN` pointing at the reachable HTTP API if its own `API_PORT` differs. Both API and workers load the dedicated `.runtime/deepseek.env`; do not snapshot model keys inside a Cube template.

The [Cube pre-warm guide](https://github.com/TencentCloud/CubeSandbox/blob/master/docs/guide/tutorials/prewarm-template-service.md) recommends a readiness probe that passes only after the Agent session is initialized, a resident process, reconnecting external sockets after restore, and an explicit concurrency model (session pool or one task per sandbox). Its [benchmark report](https://github.com/TencentCloud/CubeSandbox/blob/master/docs/blog/posts/2026-06-01-cubesandbox-perf-benchmark.md) measures sandbox operations on different hardware and warns that throughput depends on workload. Neither result proves this application's JCode turn capacity; the present Cube template still lacks a resident JCode/Bridge.

Cube's separate [1/2/4/8 base-instance creation probe](cube-concurrency.md) measured sandbox creation and health, not active business turns. The current base template contains only the lightweight Python interpreter, not JCode/Bridge. A guest socket probe reached `api.deepseek.com:443` when internet access was enabled, but connections to the host's temporary HTTP listener at `192.168.100.122:3101` were refused and attempts via `100.64.0.1` timed out. The existing business API also listens only on `127.0.0.1:3100`. Before resident JCode can use PostgreSQL-backed sessions, build a dedicated template, provide a narrowly scoped guest-to-API route, and verify recovery, permission fencing, two-case isolation, queueing, TTFT, tool latency, resource use, and cleanup under real model traffic. No Cube-resident performance or capacity claim is supported yet.

Local instance check, 2026-09-23: after the full `npm run check` passed, the idle `erp-agent-dev-api` process on port 3100 was migrated and restarted with the new binary. `/ready` returned 200. A fresh isolated account sent a short real DeepSeek Flash turn; the API returned `queued`, then `running` at about 0.5 s, then `completed` at about 4.1 s with one reasoning step. PostgreSQL recorded 221 ms from message creation to worker start and 1,733 ms to first output token before event-driven wakeup. After deploying the wakeup change locally, a second short real turn completed; PostgreSQL recorded 6 ms to worker start, 3,616 ms to first output token, and 3,641 ms to completion. Four more independent cases then sent short real DeepSeek Flash turns concurrently: all completed in a 4,045 ms batch, each started in 12-13 ms, and first tokens arrived in 3,240-3,602 ms. This establishes concurrent admission and completion for this small local real-model workload; it does not establish sustained throughput or Cube-resident capacity. The 4173 browser reasoning test completed three real turns (`none`, `low`, `high`) and showed a completed reply with an expandable high-effort reasoning step. The Web label for the transient `queued` state is `Queued`; it is distinct from model thinking.
