# JCode + 自建 Web：ERP 智能体 Demo 架构

日期：2026-09-21。本文是源码与官方文档核对后的设计建议，尚未安装、部署或完成跨组件联调。项目主分支持续变化，实施时应固定版本。

更新：PostgreSQL 分域业务 API 已实现；本文的 Agent/ERP/Cube 集成仍为设计。用户重新讨论 JCode 的内外放置方式，下文及架构图所示“沙箱内”改为优先验证的候选，最新比较和官方依据以[两种放置方式调研](cube-runtime-placement.md)为准。

当前架构图：同目录 `cube-jcode-server-architecture.svg` / `.png`，包含首版 Cube 隔离部署与异步解析 Worker。

## 1. 推荐路线

根据当前选型，使用 JCode 的 Rust Harness，自建业务 Web，通过业务 MCP 接入 ERPNext 和 OpenViking。首个 Demo 使用真实运行的 ERPNext 与合成民品数据，完成变更对比、原文引用、人工确认、单据写入和执行跟踪。

建议技术组合：React + TypeScript Web、Node.js + TypeScript 业务后台、CubeSandbox、沙箱内 SDK 桥接服务与独立 JCode 运行时、关系数据库、业务 MCP 网关。CubeSandbox 纳入首版，承载 JCode 的服务端隔离运行环境；JCode 引擎使用 Rust，桥接服务使用官方 TypeScript SDK。

JCode 源码核对基准：`2a4edaa02057ac994a601311c4f03ed450e1b3c9`。实施时还需固定相匹配的 SDK 和运行时版本。

| 已确认能力 | 在本项目中的用途 | 尚需验证 |
| --- | --- | --- |
| Rust 运行时与 Agent Loop | 复用模型调用、上下文管理和工具循环 | 目标模型的实际工具调用质量 |
| TypeScript SDK、NDJSON 本地套接字、流式事件 | 后台驱动会话，转成浏览器 SSE | 断线与重启后的业务恢复 |
| `[tools]` 配置中的 `enabled` / `disabled` / `disable_base_tools` | 限定工具集合，关闭通用编码工具 | 新会话、恢复会话和所有调用入口均执行限制 |
| 工具执行层的会话策略检查 | 调用阶段拒绝未授权工具 | 动态 MCP 别名和间接调用不能绕过限制 |
| stdio MCP | 连接受控业务 MCP 网关 | 与 OpenViking HTTP MCP 的桥接兼容 |

Rust 降低的是运行时自身的资源开销，不能据此推断模型显存、推理速度或整体 GPU 成本。

## 2. 组件职责

### Web 与业务后台

Web 展示四个相互关联的视图：需求变更、影响分析、人工确认、执行台账。对话用于发起分析和追问，结构化视图用于核对数量、版本、依据与动作。

业务后台保存用户身份、变更案件、审批记录、输入快照、执行结果与审计日志；提供实时事件流。任务调度器根据 ERP 事件或轮询推进案件，不要求一个模型循环持续运行几天。

原型阶段这些模块可以放在同一个后台进程中，不必拆成一组微服务。任务、审批和审计可先使用一套关系数据库。

### Agent Harness

采用独立 JCode 实例，保留模型调用、上下文管理、工具注册、事件流、取消、超时、重试与会话恢复。业务知识可以写成 Skill 或系统上下文，但金额、数量计算和审批规则必须在服务端执行。

浏览器只连接业务后台。后台创建或恢复 Cube 沙箱，通过受鉴权的内部 HTTP/SSE 接口访问沙箱内 Runtime Bridge；Bridge 使用 `@1jehuang/jcode-sdk`，通过同一沙箱内的本地 socket 操作 JCode。不能假设宿主机 SDK 能直接连接微虚机内部的 Unix socket。Runtime Bridge 是本项目需要实现的薄适配层。

使用独立 `jcodeHome` 保存配置和可重建临时状态，`inheritLogins: false` 配合专用模型配置，避免继承开发人员账号。用户已确定 JCode 会话、消息、todo 和压缩恢复状态存入 PostgreSQL，必须改造上游文件持久化，不能依赖该目录的 JSON/journal 或定期同步。会话与企业用户、案件、沙箱的授权映射由后台保存；沙箱销毁后从数据库恢复，详见[会话存储设计](session-storage.md)。

JCode 当前只支持 stdio MCP，HTTP/SSE 配置会被跳过。因此设计一个 stdio 业务 MCP 网关：向 JCode 暴露限定的业务工具，内部通过 HTTP 调用 ERP 适配器与 OpenViking MCP。该网关由本项目实现，不能把它写成 JCode 已有能力。

首版通过独立实例配置工具白名单，使用实际发现的工具名称，不笼统允许所有 MCP 工具。新会话、会话恢复、别名调用和重试都要验证同一限制；若公开配置不足，再对权限接入点做小范围修改。

JCode 的 `permission_request` 属于工具授权，不等于计划员批准某份变更方案。方案进入待审批后可以结束本轮 Agent；批准结果持久化，再由后台发起后续运行。浏览器关闭不应丢失审批和执行状态。

SDK 的实时事件流不保证断线期间的历史事件重放，因此业务后台另行保存带序号的事件和工具执行结果。重新连接后从业务记录恢复视图，再与 JCode 会话及 ERP 状态对账，不能通过重新执行写工具来恢复页面。

建议循环：读取案件和证据 → 选择查询工具 → 检查缺失信息 → 生成结构化建议 → 等待人工确认 → 执行已批准动作 → 结束本次运行。后续 ERP 事件可触发新一轮运行。

首版保留 todo，用于 Agent 分解和记录当前分析步骤，例如核对料号、查询库存、检查版本、生成建议。todo 展示在 Web 中，并关联案件；若原生 todo 的事件或持久化契约不合适，可提供业务版 todo 工具。

todo 是 Agent 的工作计划，不能作为采购、生产或交付已经完成的证据。执行台账由业务后台根据 ERP 状态更新；只有查询验证后，Agent 才能将相应检查步骤标为完成。

首版不向业务 Agent 注册通用 Bash。read、write 等文件能力也不必原样照搬编码 Agent；用读取原文、获取附件、生成报告等明确接口替代。工具集合采用“todo + 受控资料读取 + ERP MCP + 知识库 MCP”，最终名称以所固定版本的实际 schema 为准。

### 提示词与上下文适配

必须修改。JCode 默认系统提示词明确定位为 coding agent，包含提交代码、使用 todo 和优先 swarm 等要求。保留 todo 的规划能力，删除提交代码与默认 swarm 等无关指令，重写业务身份与流程，不能仅在末尾追加一段 ERP 角色说明。

采用四层上下文：固定的业务身份和边界；经确认的需求变更处理流程；本轮案件、用户身份、数据版本和审批状态；通过工具查询的 ERP 事实与原文证据。前三层由服务端生成，工具返回内容作为待核验资料，不得变成系统指令。

内部 `build_system_prompt_split` 存在 `system_prompt_override` 分支，但当前分支直接返回静态文本和空动态文本，跳过后续 Skill、记忆、案件提醒等拼装。稳定会话 API 未显示完整系统提示词替换参数。因此设计一个受服务端控制的业务 prompt profile 接入点，保留静态/动态分层，并测试创建、恢复、压缩上下文后的实际模型输入；这是需要完成的 JCode 适配工作。

首版关闭与此业务无关的默认 Coding Skill、swarm 指令及自动记忆注入。案件事实从业务数据库恢复，规范证据从限定范围的知识库查询。任务记忆后续可以启用，但必须限定客户和案件范围。

提示词负责让模型识别增量/累计/新版总量、需求类型、修订版、缺失信息，以及准确描述建议与执行结果；工具白名单、审批、幂等和版本检查仍由代码实施。业务 Prompt 草案见 [prompts/erp-agent-system-prompt.md](../../prompts/erp-agent-system-prompt.md)，尚未接入运行时。

### ERP MCP 与适配器

MCP 定义业务工具及输入输出；适配器调用 Frappe API，并负责权限、字段映射、流程状态、幂等与错误归一化。Demo 中可以合并为一个服务。

建议首批工具如下，工具名称为本方案设计，并非 ERPNext 原生 MCP：

| 工具 | 作用 |
| --- | --- |
| `get_demand_baseline` | 获取对应客户、零件、版本的有效需求与数量口径 |
| `resolve_item_mapping` | 查询客户料号与内部物料号；多义映射返回待确认 |
| `get_supply_snapshot` | 获取库存占用、在制、在途、相关单据及更新时间 |
| `evaluate_change` | 按明确规则计算差异、净需求与交期风险 |
| `prepare_change_proposal` | 保存建议、依据、前置条件和预计动作 |
| `execute_approved_proposal` | 验证服务端审批记录并执行批准的动作 |
| `get_execution_status` | 查询关联采购、生产和交付单据的实际状态 |

审批必须绑定具体 proposal 版本、动作清单与 ERP 数据版本。模型传入 `approved=true` 不构成审批。执行前若库存或订单变化，重新评估；重试通过幂等键避免重复建单。

跨单据写入要记录每一步成功与失败，允许重试或人工处理，不能假设多个 API 调用天然构成一个事务。

ERPNext 的已提交单据必须遵循其修改、取消和修订流程。首版可创建合规草稿或关联调整单据，不能承诺任意覆盖生产中订单。

### OpenViking 与 MinerU

OpenViking 适合作为 Agent 的分层上下文与资料检索服务。可以做出 Wiki 式资料目录和浏览体验，但它不等于一套完整的文档审批、版本治理与企业门户。

已核对：OpenViking 当前文档提供内置 HTTP MCP；PDF 解析实现包含 MinerU 调用路径，访问 `/file_parse`。这里的 HTTP 服务可以部署在内网。实际组合仍需固定版本并验证请求、返回格式、图片与引用是否兼容。

建议管线：原件归档 → 解析队列 → MinerU / 结构化表格读取 → 元数据校验与引用定位 → OpenViking 索引。

批量解析采用独立异步 Worker，上传 API 只完成原件归档和任务登记并返回 job_id，不等待全部文档解析。首版使用业务数据库中的任务/步骤记录作为状态依据，通过事务 outbox 向持久队列投递；队列中传递文件引用、版本和任务 ID，不携带大文件内容。

Worker 依次完成解析、元数据和引用校验、索引构建。任务状态为 queued、parsing、validating、indexing、ready，也可转 failed / needs_review / cancelled；UI 展示各阶段进度，Agent 通过状态工具或完成事件得知结果，不占着一轮模型循环持续轮询。

采用至少一次投递、租约/心跳、有限重试和失败任务记录，按租户、原件哈希、解析器配置及目标版本实现幂等。重试先检查已完成阶段，避免重复解析或索引。只有索引完成并通过校验，才切换对应版本的可检索状态；中间结果不能被当作完整正式资料检索。任务取消后也要阻止迟到结果发布。

CPU 表格处理、GPU 文档解析和索引构建使用分别受控的 Worker 并发，可先由同一个 Worker 程序提供不同角色，不必首版拆多个代码仓库。队列实现可采用 Redis Streams，但需配套持久化、消费者 pending 处理与重投递；Redis 队列本身不能替代上述业务状态和幂等设计。

Excel 需求表优先用结构化表格解析，保留工作表、行列、单位和公式结果。PDF 扫描件走 MinerU，工程符号和关键数量解析不确定时转人工核对。能提取文本不等于提取准确。

资料至少携带客户、项目、零件号、修订版、有效期、文件类型、权限、原件哈希以及页码/单元格定位。检索前在服务端限定授权范围，查回原文时再次校验版本与来源。目录路径不是权限控制的替代品。

规范资料、Agent 历史记忆、ERP 当前事实和业务任务状态分别管理。Agent 总结只能作辅助，不能自动覆盖正式版本资料。

### CubeSandbox

CubeSandbox 纳入首版，作为整个 JCode 实例的隔离运行层。服务器部署本身不强制要求微虚机，但本项目需要在共享服务器上管理多个 Agent 会话、附件、运行时进程及生命周期，因此选择 Cube 承担这一职责。

沙箱内放置 Runtime Bridge、JCode、stdio MCP 网关和案件临时工作目录。沙箱外放置 Web/业务后台、Cube 控制面、ERP 适配器与 ERPNext、知识库权限服务与 OpenViking、关系数据库、原件/产物存储和共享模型服务。

业务后台调用 Cube API 创建、恢复、暂停和释放沙箱；模型不能调用这些管理接口。首版按“企业租户 + 用户 + 案件会话”绑定沙箱，同一活跃会话的多次模型/工具调用复用实例，不为每次 MCP 调用新建微虚机。采用少量预热的干净模板实例降低冷启动等待；绑定后隔离使用。历史案件不永久占用运行实例，空闲会话保存检查点后暂停或释放，重新访问时恢复。跨用户或跨案件默认不复用已用工作目录，不依赖简单清理来保证隔离。

镜像模板预装固定版本的 JCode、Node、SDK、桥接服务和业务 MCP 网关，不预置用户数据或长期业务凭据。首版展示两个会话的目录/进程隔离、配额限制及暂停恢复。启动延迟按完整 JCode 链路实测，不能套用 Cube 的基础沙箱启动宣传指标。

配置 CPU、内存、磁盘、空闲时限、沙箱访问令牌与网络出口，只允许访问授权的模型和业务网关。网络隔离不能替代 ERP 与知识库中的业务权限。ERP 高权限凭据保留在沙箱外的适配器；沙箱持有范围受限、可撤销的访问凭据。Cube 管理端口不对浏览器和 Agent 公开。

保留 todo、受控 read 与业务 MCP，不向模型开放通用 Bash。运行时启动进程和 MCP 服务不等于授权模型任意执行命令；有沙箱也不意味着必须给模型 Bash。

等待人工审批时先保存业务状态和运行时检查点，再按策略暂停。恢复后重新验证身份、凭据、ERP 版本与未完成写入结果。快照中的网络连接和令牌可能失效，快照也不会撤销外部 ERP 已完成的写入。归档产物与必要状态后才能销毁沙箱。

官方快速入门包含 KVM/PVM、Linux 内核、glibc、XFS reflink 与磁盘要求。服务器条件核查是部署前置步骤；如果现有 GPU 主机不适合，可用独立 CPU 主机承载 Cube，经内网调用模型服务。

固定解析服务与 GPU 模型服务部署在沙箱外，不为每个用户重复加载模型，不将 Cube 当作 GPU 推理资源调度器。

## 3. 一次可演示的业务闭环

1. 在 ERPNext 建立两家客户、几个物料/BOM、销售订单、库存、在制和采购数据。知识库放入两家客户相近料号及新旧修订版资料，全部使用合成民品数据。
2. 导入新需求：例如某零件新版总量从 1,000 增至 1,300，交期提前 3 天。系统明确这是新版总量，而非再追加 1,300；需求属于预测、订单还是交付指令必须可辨识。
3. Agent 查询有效基线、客户料号映射和 ERP 供需快照，引用对应客户和版本的资料。字段不清或映射一对多时进入待确认。
4. 规则服务计算需求差异和物料缺口，Agent 解释影响并生成采购申请、生产调整建议。交期风险依据数据判断；没有工时、设备、日历等约束时不声称完成精确排产。
5. 计划员在 Web 中核对差异、依据和动作后批准。后台校验数据仍有效，再创建 ERPNext 中的相应草稿或允许的业务单据，展示真实单号和链接。
6. 在 ERPNext 中模拟采购或生产人员处理单据，后台通过事件/轮询刷新执行台账。已建单、已批准、已收货和已完成生产分别显示。

需要至少演示三种异常：旧版本检索被排除；重复执行不重复建单；批准后数据变化触发重新评估。

## 4. 服务器部署

正式内网运行通常部署在服务器上，用户通过浏览器访问；研发 Demo 也可以先在开发机完成。

单机原型按逻辑服务部署：Web/业务后台、Cube 控制面与 JCode 沙箱、ERPNext 及其数据库与缓存、OpenViking、文件存储、解析 Worker、模型服务。逻辑上分层不等于每层需要一台服务器；Cube 也可部署在独立 CPU 节点，经内网共享 GPU 模型服务。

GPU 主要供 LLM、Embedding/Reranker 和部分解析模型使用，ERP、MCP 与大部分业务服务不需要 GPU。将在线问答与批量解析分队列，为在线请求留资源，批处理限并发并支持排队。

目前缺少服务器配置，不能给出可支撑并发或是否扩容的结论。记录模型和量化配置、峰值显存、排队时间、P95 响应时间、输出速度、并发任务数、解析页数/分钟和失败率，再用同机混合负载测试决定共用与扩容。

## 5. 性能设计与验证

高性能覆盖整条业务路径，不能由 Rust、微虚机或某个组件的宣传指标推导。当前没有服务器配置和业务负载基线，以下是设计与测量方案，不是容量或延迟承诺。

### 关键路径

在线请求经过业务后台、沙箱内 Bridge、JCode、模型服务和业务工具；这些进程保持常驻或预热。避免逐条消息启动 JCode、逐次调用初始化 MCP、每个会话重新加载 GPU 模型。SDK Bridge 与 stdio 网关是两个不同协议边界，但可以在沙箱内用一个轻量服务包管理，不必拆成多组远程服务。

浏览器提交案件后先获得确认与事件订阅，分析由后台 Worker 执行并通过 SSE 返回进度。耗时解析和 ERP 执行采用可查询的任务记录，不能让前端请求或 MCP 连接无限等待。

### 各层优化

| 层 | 首版做法 | 需要观测的代价 |
| --- | --- | --- |
| Web 与后台 | 异步 I/O、连接池、SSE 合并小片段、分页原文与日志；重计算交给 Worker | 事件循环延迟、队列长度、序列化时间、连接数与内存 |
| Cube | 固定模板、少量干净预热实例、活跃会话复用、空闲暂停、并发配额 | 完整业务就绪时间、暖恢复时间、每活跃实例 RSS/CPU、池命中率 |
| JCode | 限定工具 schema、分层 Prompt、上下文压缩保留关键业务字段、限制无效重试 | 每案件模型轮数、输入/输出 token、工具调用数与重复查询 |
| 模型服务 | 模型常驻、按实测配置连续批处理和前缀缓存、限制并发与输出长度 | TTFT、输出速度、KV cache、峰值显存、排队与取消回收时间 |
| ERP | 一次获取相关供需快照；独立只读查询有界并行；复用连接并限流 | ERP P95/P99、查询次数、数据更新时间、超时率与服务器压力 |
| 知识检索 | 先按客户/零件/版本限定范围，返回少量相关段落和定位；按需读原文 | 检索与重排时间、引用命中与版本正确率、上下文大小 |
| 文档入库 | 持久队列 + 异步 Worker，阶段幂等、按资源限并发、解析结果复用 | 页数/分钟、积压量、解析质量、GPU 峰值和在线请求受影响程度 |

缓存按用户授权范围、客户、版本和数据时点区分。资料索引缓存可长于 ERP 实时库存快照；执行批准方案前仍重新验证 ERP 状态。不能为了缓存命中率放宽版本或权限边界。

在线分析、ERP 写入和批量解析使用不同的并发预算。在线模型请求优先获得资源，批处理用剩余预算；同卡模型争用无法有效控制时，错峰运行或分卡/分节点部署。Cube 管理 CPU 沙箱，不代替 GPU 推理调度。

对只读查询可以合并和有限并行；有依赖或会改变业务状态的步骤保持有序。工具超时、模型重试与后台任务重试要有统一预算，防止服务变慢时重试倍增。每租户/用户设活跃案件上限，达到容量时排队或明确拒绝，避免拖垮所有会话。

### 测量与验收

统一 trace 关联 case_id、session_id、sandbox_id、模型轮次和工具调用 ID。最少记录以下时间段：排队、沙箱就绪、上下文准备、模型首字、模型生成、每个工具调用、审批等待、ERP 执行。人工等待单列，不能混入系统响应性能。

分别测冷启动、预热启动、暖恢复和活跃会话；再测知识问答、完整变更分析、已批准方案执行、在线分析与批量解析混合负载。先测单请求，再逐步增加并发，直到延迟、错误率或资源饱和触及事先约定的阈值。

验收同时报告 P50/P95/P99、完成案件数/分钟、超时/失败率、token/案件、CPU/RAM/显存，以及数据和引用准确率。包含两个用户并行、排队取消、ERP 变慢、断线恢复及重复执行场景。不能只用一次成功请求或平均延迟宣称高性能。

先以客户端实际并发、目标文档量和可接受响应时间确定 SLA。没有这些数据时，交付容量曲线与瓶颈测量结果，避免预先承诺某台服务器支持多少用户。Node 后台与 Bridge 首版以减少协议重复和阻塞为重点；只有测量表明它们成为瓶颈，才考虑用 Rust 重写对应热点。

## 6. 实施顺序与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| 沙箱验证 | Cube 宿主检查 + 固定模板 + Runtime Bridge | 两个会话隔离；CPU/内存与网络策略有效；通过鉴权接口驱动 JCode |
| 运行时验证 | JCode SDK + 业务 Prompt + 工具白名单 + stdio 网关 | 编码默认指令已替换；案件上下文正确注入；无关工具被执行层拒绝 |
| 集成验证 | 自建 Web + JCode + ERPNext + OpenViking | 真实查询 ERP；知识检索带正确来源；实际工具调用可追踪 |
| 业务闭环 | 变更案件 + 建议 + 审批 + 写入 + 跟踪 | ERP 中看到真实单据；重试不重复；状态变化可回到台账 |
| 客户演示 | 业务 Web 页面 + 可重置样本集 | 正常与异常场景可稳定重复演示；人工确认点清晰 |
| 恢复验证 | 会话重连 + 沙箱暂停恢复/重建 + 后台重启 | 待审批状态不丢失；失效连接/凭据可恢复；已成功写入不重复执行 |
| 资源评估 | 目标服务器混合负载实测 | 用客户认可的响应目标判断容量，不以框架语言推算容量 |

正式对接客户 ERP 时，复用业务工具契约和界面，重做并验证字段映射、状态转换与交易语义。不能把 ERPNext 成功演示等同于客户 ERP 已集成。
